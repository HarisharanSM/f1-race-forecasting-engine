# F1 race forecasting engine

A Python system for **qualifying positions** and **Grand Prix finishing order**, with up to five scenarios, an optional LLM, and feedback-driven learning.

Forecasts can use a **trained PyTorch Transformer**. Neural training runs locally without an API key; the LLM remains optional for research/extraction. See [ML training and backtesting](docs/ML.md) for the architecture, chronological splits and checkpoint usage.

The primary workflow uses **actual 2024–2025 qualifying and Grand Prix results**, observed track weather, and archived day-ahead weather forecasts. See [real-data setup and limitations](docs/REAL_DATA.md).

```sh
uv sync --all-extras
source .venv/bin/activate
f1-forecast fetch-history --seasons 2024 2025 \
  --output data/processed/real-history-2024-2025.json
f1-forecast backtest data/processed/real-history-2024-2025.json --model transformer \
  --test-from-season 2025 --min-train-events 8 --validation-events 2 \
  --output artifacts/real-data/backtest.json --save-model artifacts/real-data/model
f1-forecast predict next-session.json --ml-model artifacts/real-data/model \
  --output artifacts/next-forecast.json
```

`next-session.json` must contain the next event's confirmed inputs; it is not generated by the historical collector. Choose new output paths when repeating an import or saving a checkpoint. Network access is required for collection; training runs locally without API keys.

This remains a research model. Results and weather are real; some historical inputs are explicitly reconstructed. Car pace uses earlier-result proxies, unsupported traits retain neutral priors, and archive revisions prevent a strict event-time-vintage accuracy claim. Missing classifications or weather are excluded rather than replaced with fictional data.

## Read the results

Open the generated **`artifacts/real-data/backtest-report.html`** in a browser. Choose a year and circuit, then Grand Prix or sprint qualifying/race. Each weather scenario has a driver table with forecasted position, confidence, actual position, and a position range. A separate actual-results table and ML feedback audit follow. The companion CSV contains every scenario table.

The combined report includes **233 held-out forecasts**: 178 for 2020–2023 and the existing 55 for 2025, with **331 actual session records** across 2019–2025. Training-only sessions are clearly labelled. Shared Friday qualifying in 2021–2022 appears in both separately trained formats. Earlier-year weather inputs use prior practice observations carried forward as estimates. See [earlier-season results and limitations](docs/EARLIER_SEASONS.md) and [report instructions](docs/REPORTING.md).

## Inputs and outputs

| Session | Required inputs | Outputs |
| --- | --- | --- |
| Qualifying | Drivers, teams, car ratings, circuit, forecast weather, prediction cutoff | Up to five scenarios, complete rankings, pole probabilities, position distributions |
| Grand Prix | Same inputs plus **actual qualifying order**; optional penalty-adjusted grid | Up to five scenarios, most likely winner, complete rankings, win/podium/retirement probabilities |
| Feedback | Verified classification, actual weather, incidents, availability time, sources | Evaluation metrics, updated numerical model, future LLM memory, training examples |

“Standings” means the session finishing order, not championship points. `winner` is the driver with the highest win probability (pole probability for qualifying). `standings` are sorted by expected position, so their first driver can differ from the most likely winner: greater win potential can coexist with greater retirement risk.

Each driver also gets an 80% marginal position interval (`p10_position`–`p90_position`) and a probability for each finishing position. Scenario probabilities sum to one. Every simulated order contains every entered driver exactly once.

See `examples/qualifying.json`, `examples/race.json`, and the contracts in `src/f1_forecast/models.py`. The example files use four fictional drivers for readability; the demo uses 22. All ratings are **[0, 1], higher means better**. Low cooling, tyre-management, or cornering ratings represent weaknesses. Free-text capabilities, weaknesses and notes inform the LLM when enabled; the numerical model uses ratings.

## Predict and apply feedback

```sh
f1-forecast --database artifacts/example.sqlite3 predict examples/qualifying.json \
  --simulations 5000 --max-scenarios 5 --output artifacts/qualifying-forecast.json

# Replace FORECAST_ID with the id in the saved forecast.
f1-forecast --database artifacts/example.sqlite3 feedback FORECAST_ID examples/qualifying-actual.json

f1-forecast --database artifacts/example.sqlite3 predict examples/race.json \
  --output artifacts/race-forecast.json
f1-forecast --database artifacts/example.sqlite3 feedback RACE_FORECAST_ID examples/race-actual.json
```

`--database` is a global option: place it before the subcommand. Keep fictional examples separate from real forecasts. Old inputs cannot be predicted using a model trained on later results; use a fresh database or the backtest command.

Supply `starting_grid` to account for penalties: an ordered list of every entered driver, with pit-lane starters after grid starters. Without it, actual qualifying order is used and the forecast reports that assumption. A withdrawal requires an updated roster and matching classification; incomplete or mismatched fields are rejected.

## Live data collection

Collectors use [Jolpica](https://github.com/jolpica/jolpica-f1/blob/main/docs/README.md) for schedules/classifications, [OpenF1](https://openf1.org/docs/) for observed weather and race control, and [Open-Meteo](https://open-meteo.com/en/docs) for forecast weather. Raw responses and retrieval times are archived under `data/raw/`. Requests have timeouts and bounded retries. Provider terms, access restrictions and publication delays apply.

```sh
# Replace YEAR, ROUND and LAPS with the desired event's values.
f1-forecast fetch-event --season YEAR --round ROUND --session qualifying \
  --laps LAPS --output data/processed/qualifying-input.json
f1-forecast fetch-event --season YEAR --round ROUND --session race \
  --laps LAPS --output data/processed/race-input.json
```

Live weather collection requires a session in the next 15 days. Race inputs use that event's published qualifying results for the roster and order. Qualifying inputs use the previous race's **provisional roster**; check substitutions. For a season opener, supply a confirmed roster yourself. Car, driver and circuit ratings start neutral and require current evidence. Fetching a roster alone does not establish pace. Lap count is supplied explicitly because upcoming schedules may not provide it.

## LLM research, extraction and prediction

Export the settings documented in `.env.example`; `.env` files are not automatically loaded.

```sh
export OPENAI_API_KEY='your-api-key'
export F1_LLM_MODEL='your-supported-model-id'

# AI web search for an upcoming real session; advances the cutoff to retrieval time.
f1-forecast research data/processed/race-input.json \
  --output data/processed/researched-input.json --report artifacts/research.json

# Convert supplied source documents into bounded car-trait estimates.
f1-forecast extract data/processed/researched-input.json documents.json \
  --output data/processed/enriched-input.json --report artifacts/evidence.json

# LLM scenario planning + LLM outcome ordering + numerical simulation.
f1-forecast predict data/processed/enriched-input.json --llm --output artifacts/forecast.json
```

Choose a model supporting [Responses structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs); research also requires [web search](https://developers.openai.com/api/docs/guides/tools-web-search). There is no hardcoded model alias. Research searches Formula1.com and FIA.com, preserving citation metadata. It adds an **unverified synthesis** to the LLM context and does not automatically change the confirmed roster or grid. Live research is disabled for past sessions.

`documents.json` is a list of source/text objects:

```json
[
  {
    "source": {
      "url": "https://your-source.example/report",
      "retrieved_at": "2026-09-04T08:00:00Z",
      "published_at": "2026-09-04T07:00:00Z",
      "note": "Source report copied at the recorded time"
    },
    "text": "The exact source document text goes here."
  }
]
```

Extraction requires exact supporting quotes and known team IDs. Low-confidence claims are ignored; accepted rating changes are bounded. A matching quote establishes traceability, not correct interpretation. Sources must predate the snapshot cutoff. Review the saved evidence report. LLM refusals or malformed responses raise errors instead of silently falling back. A numerical-only prediction needs no credentials.

## Obtain actual results

```sh
# Supply the OpenF1 session_key for the exact qualifying session or Grand Prix.
f1-forecast fetch-feedback FORECAST_ID --session-key SESSION_KEY --output artifacts/actual.json
f1-forecast feedback FORECAST_ID artifacts/actual.json

# LLM fallback for unstructured reports; output is always unverified.
f1-forecast extract-feedback actual-documents.json --event-id EVENT_ID --session race \
  --output artifacts/extracted-actual.json
```

The structured collector cross-checks session type, year, timing and the full driver field. Missing data causes an error; actual weather is never replaced with forecast weather. Wet exposure is the fraction of available OpenF1 samples reporting rain; missing samples and rainfall-versus-track-wetness differences remain limitations. Event classification is conservative and can be supplemented with reviewed reports.

LLM-extracted feedback always has `verified: false`. Review its classification, weather, incidents and sources, then set it to `true` before submitting. Identical repeated feedback does not train twice. Conflicting corrections require rebuilding from corrected history. Synthetic and real data must use separate databases.

## Closed-loop learning

1. **Numerical updates:** separate qualifying/race weights and driver/team effects update from verified results. Retirements, known collisions and penalties are masked from pace learning. Mechanical problems update a reliability estimate. Actual wet exposure adjusts the weather prior.
2. **LLM memory:** earlier verified sessions of the same type enter future outcome prompts, excluding the target event and unavailable feedback. This changes context, not LLM weights.
3. **LLM fine-tuning:** accumulated real input/result pairs train the outcome-ordering head through an explicit export and job-submission workflow.

## Backtest before claiming improvement

```sh
f1-forecast backtest examples/backtest.json --output artifacts/backtest.json
```

Input is a JSON list of `{"snapshot": {...}, "feedback": {...}}` pairs. The supplied example file is fictional and is only a test fixture. Use the real historical dataset above for archived-result evaluation, or snapshots captured before each session for a strict point-in-time evaluation. The backtest sorts by prediction cutoff and learns only when feedback would have become available. It compares an adaptive numerical model with a frozen baseline on expected-position MAE, pairwise accuracy, winner accuracy, winner Brier score and position log loss.

Lower MAE/Brier/log loss and higher ranking/winner accuracy are better. Updates can worsen predictions; improvement is not assumed. Reserve later weekends or seasons for an untouched test set. Backtesting excludes the LLM because historical results may be in its pretraining data. Timestamp checks cannot prove source truth or remove LLM recall leakage.

## Retrain the LLM outcome head

```sh
f1-forecast export-training --output artifacts/training

# Explicitly submits a billable remote job using your account.
f1-forecast fine-tune artifacts/training --base-model ELIGIBLE_BASE_MODEL_ID
f1-forecast training-status JOB_ID

# Adopt only after evaluating the completed candidate on later unseen sessions.
export F1_OUTCOME_MODEL='your-fine-tuned-model-id'
```

Export uses verified real feedback, grouping qualifying/race sessions from the same weekend in the same split. Latest weekends are held out; delayed training labels unavailable before validation are purged. At least three event weekends and **10 training sessions after splitting** are required. This is a minimum for the workflow, not sufficient evidence of quality. Synthetic fixtures are excluded and file hashes are checked before upload.

Inputs are the original outcome-head messages. Targets contain only the actual `predicted_order`. Actual target-session weather/incidents are not added to prediction inputs. Earlier feedback may appear in memory; actual qualifying results legitimately appear in race inputs. An observed finishing order is a noisy training label, not a deterministic outcome the model should always have predicted.

The [supervised fine-tuning API](https://developers.openai.com/api/docs/guides/supervised-fine-tuning) requires an eligible base model and account access. Job submission saves an ID and does not adopt the candidate automatically. The outcome model must support the structured output contract. No LLM training job has been run for this repository.

## Python and HTTP APIs

```python
from pathlib import Path
from f1_forecast.models import Snapshot, Feedback
from f1_forecast.service import ForecastService

service = ForecastService("artifacts/my-model.sqlite3")
snapshot = Snapshot.model_validate_json(Path("examples/qualifying.json").read_text())
forecast = service.predict(snapshot, simulations=5000, max_scenarios=5)
print(forecast.winner)
actual = Feedback.model_validate_json(Path("examples/qualifying-actual.json").read_text())
print(service.feedback(forecast.id, actual))
```

Pass `llm=LLM()` to `ForecastService` to enable LLM scenarios and ordering. Collectors and extraction are also Python APIs in `data.py` and `llm.py`.

```sh
uvicorn f1_forecast.api:app --host 127.0.0.1 --port 8000
```

Open [API documentation](http://127.0.0.1:8000/docs). Routes: `POST /predictions`, `GET /predictions/{id}`, `POST /predictions/{id}/feedback`, `GET /model`, `GET /health`. Prediction bodies contain `snapshot`, optional `simulations`, `seed`, `max_scenarios`, `plan` and `use_llm`. The API is for local use and has no authentication layer.

## Algorithm and limits

```text
strength(i,s) = stage_weights · features(i,s)
                + learned_driver_effect + learned_team_effect
                + bounded_LLM_order_prior
performance(i,s) = strength(i,s) + execution_noise + disruption_noise
```

Features cover car pace, driver skill, weighted car/circuit fit, tyre management, actual grid, wet performance, strategy/pit crew and cooling under heat. The LLM prior is bounded to ±0.15 score units. Race simulations sample mechanical and incident retirements; retired cars rank by sampled distance completed behind finishers. Scenario distributions are mixed by their probabilities. Pairwise logistic updates learn from incident-free comparisons. Initial weights, weather splits, uncertainty and reliability priors are explicit heuristics, not fitted F1 parameters.

The default planner uses one to three weather regimes within the requested maximum; LLM/custom plans can use five. A single scenario uses expected wet exposure as an approximation. The simulator does not implement Q1/Q2/Q3 elimination, lap-by-lap traffic, tyre compounds or pit timing, detailed safety-car bunching, correlated crashes, cancellation or FIA classification edge cases. Lap count is retained as context; baseline reliability is per-session. Retired cars finishing ahead of running cars, DNS/DSQ, and pit-lane starts are approximations.

Future model development should derive ratings from historical pace/telemetry, fit coefficients on rolling training windows, calibrate probabilities and compare LLM contributions with the numerical baseline. All features must have been available at each prediction cutoff.
